01

전체 구조: 세 곳에서 도는 프로그램

제어판은 한 프로그램이 아니라, 역할이 나뉜 몇 개의 프로세스가 서로 메시지를 주고받는 구조입니다. 사람이 보는 화면은 브라우저이고, 실제 일은 PC마다 떠 있는 제어판 서버(omx_web.py)가 받아서 필요한 프로그램을 띄웁니다.

점선은 Tailscale 위의 SSH 연결 하나입니다. 네트워크에 열린 포트는 없고, 모든 서버는 127.0.0.1에서만 받습니다.

어디서무엇이 돈다언제
브라우저omx_panel.html: 버튼·표·카메라 화면. 1초마다 /api/status를 읽어 다시 그림제어판을 여는 동안
제어 PComx_web.py(상시) → 작업마다 omx_run.py 한 개바탕화면 아이콘으로 켜면 계속
GPU 노트북omx_web.py(상시, 계정마다), omx_infer.py serve(상시), 학습할 때 omx_train.py·omx_train_queue.py설치 후 계속
v3에서 바뀐 핵심: v2까지는 LeRobot의 lerobot-record 안쪽 함수를 바꿔 끼워 녹화·평가를 했습니다(omx_record.py). LeRobot 0.6.1에서 녹화 스크립트가 정책 실행을 빼면서, v3는 제어 루프를 omx_run.py가 직접 갖습니다. LeRobot은 로봇 클래스·카메라·데이터셋·정책 같은 "부품"으로만 씁니다.

03

흐름 ①: [녹화 시작] 버튼에서 로봇이 움직이기까지

녹화를 예로 듭니다. 텔레옵과 평가도 같은 길을 지나고, 4단계의 명령만 다릅니다.

  1. 화면이 API를 부른다 (omx_panel.html)

    버튼을 누르면 자바스크립트가 입력값을 모아 POST로 보냅니다. "로봇 옆에 사람이 있음" 체크가 confirm으로 함께 갑니다.

    await api("/api/record", { confirm, name, task, episodes, episode_s, reset_s, upload, ... })

  2. 서버가 받는다 (omx_web.py · Handler.do_POST)

    Handler는 파이썬 표준 http.server입니다. 경로를 보고 함수를 고릅니다. /api/teleop, /api/record, /api/eval/start는 confirm이 없으면 거절합니다. 제어 PC에서 학습·비교·보고서 같은 경로는 여기서 처리하지 않고 GPU 노트북으로 넘깁니다(흐름 ④).

    if self.path in ("/api/teleop", "/api/record", "/api/eval/start") and not body.get("confirm"):
    raise RuntimeError("로봇 옆에 사람이 있는지 확인하고 체크해주세요.")
...
elif self.path == "/api/record":
    self._json(start_record(body))

  3. 명령줄을 만든다 (start_record)

    데이터셋 이름을 정하고(같은 이름이 있으면 --resume=true로 이어서), 카메라 보기를 끄고(PREVIEW.stop(), 녹화가 카메라를 써야 하므로), 손목 카메라 밝기 자동 조절을 끈 뒤 omx_run.py 명령을 만듭니다. 로봇·카메라 인자(ROBOT_ARGS, CAMS_ARG, TELEOP_ARGS)는 ① 탭 "로봇 구성"에서 저장한 값으로 apply_setup()이 미리 만들어 둡니다.

    cmd = ["~/venv/il3/bin/python", "omx_run.py",
       "--robot.type=omx_follower", "--robot.port=/dev/omx_follower_2", "--robot.cameras={front: …, wrist: …}",
       "--teleop.type=omx_leader", "--teleop.port=/dev/omx_leader_2",
       "--dataset.repo_id=tkoo/1028_1030", "--dataset.single_task=pick the strawberry",
       "--dataset.num_episodes=10", "--dataset.episode_time_s=30", "--dataset.reset_time_s=15"]
JOB.start("record", cmd, info)

    협동 로봇이면 --robot.type=bi_omx_follower --robot.left_port=… --robot.right_port=…로 바뀌고 카메라가 4대(front, front_2, wrist_left, wrist_right)가 됩니다.

  4. 프로세스를 띄운다 (Job.start)

    Job은 "로봇을 쓰는 작업은 한 번에 하나"를 지키는 관리자입니다. 다른 계정이 로봇을 쓰는지 확인하고(other_robot_processes), 포트가 꽂혀 있는지 보고, 공유 잠금 파일(robot.lock)을 잡은 뒤 subprocess.Popen으로 실행합니다. 이때 표준 입력·출력을 파이프로 연결해 두는데, 이것이 이후의 "명령 보내기"와 "진행 상황 읽기" 통로입니다.

    self.proc = subprocess.Popen(cmd, cwd=LEROBOT_DIR, env=env, stdin=PIPE, stdout=PIPE, stderr=STDOUT,
                             text=True, bufsize=1, start_new_session=True)
threading.Thread(target=self._read_output, daemon=True).start()

  5. 로봇 프로그램이 돈다 (omx_run.py)

    인자를 읽고(draccus), 로봇·리더 객체를 만들고, 데이터셋을 만들거나 열고, 연결 → 안전 시작 → 에피소드 반복 → 저장 → 안전 정지 순으로 진행합니다. 자세한 내용은 흐름 ③.

  6. 출력 줄이 화면의 "단계"가 된다 (Job._read_output → _parse)

    omx_run.py가 찍는 줄을 서버가 한 줄씩 읽어 상태(info)를 바꿉니다. 화면은 1초마다 /api/status로 이 상태를 받아 그립니다.

  7. 끝나면 정리 (Job._read_output 끝부분)

    프로세스가 끝나면 종료 코드를 기록하고, 잠금을 풀고, 데이터셋에 팀 그룹 권한을 주고, 제어 PC라면 GPU 노트북으로 전송을 예약합니다(remote.sync_later(push)). 평가라면 시도별 자동 분석(fill_auto_later)도 시작합니다.

04

흐름 ②: 실행 중에 보내는 명령과 신호

실행 중인 omx_run.py에는 두 가지 통로로 지시합니다. 일상적인 조작은 표준 입력 한 줄, 급한 것은 유닉스 신호입니다. 신호는 프로그램이 무엇을 하고 있든 바로 끼어들 수 있어서, 멈춤 계열에 씁니다.

화면 버튼서버 함수보내는 것omx_run.py에서
다음으로Job.send("next")stdin next_listen_stdin → EVENTS["exit_early"]: 지금 에피소드(또는 원위치 시간)를 끝냄
다시 찍기Job.send("rerecord")stdin rerecord에피소드를 버리고(clear_episode_buffer) 같은 번호로 다시
끝내기Job.send("stop")stdin stop지금 에피소드까지 저장하고 종료
정지Job.stop()SIGINT (두 번째는 SIGTERM)_on_interrupt: 첫 번째는 끝내기와 같음, 두 번째는 바로 빠져나감(안전 정지는 그대로)
즉시 중단 (평가)Job.abort()SIGUSR1_on_abort: 정책을 멈추고 곧바로 처음 자세로 내려놓음. 진행 중 시도는 1초 이상이면 '중단됨'으로 저장
비상 정지 (평가)Job.freeze()SIGUSR2_on_freeze: 명령을 끊고 제자리 유지(토크 유지), 기록 저장, [홈 위치로 이동] 대기
홈 위치로 이동home_return()stdin homeomx_safe_start.RELEASE.set() → 처음 자세로 천천히 → 안전 정지
강제 종료Job.kill()SIGKILL (프로세스 그룹 전체)응답 없음. 팔로워는 토크를 켠 채 그 자리. 평가였다면 서버가 omx_return_home.py로 복귀
비상 정지는 "응답 확인"을 합니다. Job.freeze()가 신호를 보내고 FREEZE_WAIT_S초 안에 [omx] freeze: 줄이 오지 않으면(프로그램이 멈춰 있으면) 강제 종료로 바꿉니다. 녹화·텔레옵의 비상 정지는 처음부터 강제 종료입니다.
05

흐름 ③: omx_run.py 안의 제어 루프

로봇을 실제로 움직이는 곳입니다. 실행 순서는 main → run → (텔레옵이면 run_teleop) / run_episodes입니다.

  1. 준비 (run)

    • omx_safe_start.install(): LeRobot의 OmxFollower 클래스의 connect·send_action·disconnect를 안전 버전으로 바꿉니다. 그래서 이후 코드는 평범하게 robot.send_action()만 불러도 안전 시작이 적용됩니다.
    • make_robot_from_config: 인자의 --robot.type에 맞는 객체(OmxFollower 또는 BiOmxFollower)를 만듭니다.
    • install_live_view: 카메라 영상을 제어판에 보여 줄 쓰기 스레드를 띄웁니다.
    • _install_controls: 신호 처리기와 stdin 읽기 스레드를 겁니다.
    • 평가라면 Policy(cfg)로 모델을 준비합니다(제어 PC는 GPU 노트북에서 불러옴, 흐름 ⑤).
    • open_dataset: 새로 만들기(LeRobotDataset.create) 또는 이어서(LeRobotDataset.resume). 특징(features)은 로봇이 알려 주는 관절·카메라 목록에서 만들어서, 0.4.4 때와 같은 형식이 됩니다.

  2. 안전 시작 → 준비 구간 (warm_up)

    리더가 있는 녹화는 첫 에피소드 전에 팔로워가 리더를 따라잡을 때까지 기록 없이 돌립니다. 0.2초씩 끊어 돌며 모든 팔의 상태가 normal이 되었는지 확인하고, 이 사이의 [다음]·[다시 찍기]는 무시합니다(아직 에피소드가 없으므로). 평가는 정책이 첫 목표를 주므로 안전 시작이 첫 시도 안에서 일어나고, 그 끝 프레임을 노트에 남깁니다.

  3. 한 스텝 (control_loop)

    due = start = time.perf_counter()          # 프레임을 고정 일정(시작 + n/30초)으로: 오래 찍어도 밀리지 않음
while 지난 시간 < episode_time_s:
    if EVENTS["exit_early"]: break          # 다음으로 · 다시 찍기 · 끝내기 · 신호
    obs = robot.get_observation()           # 관절 위치 + 카메라 최신 프레임
    _show(obs)                              # 실시간 화면용으로 프레임 참조만 넘김
    if policy:  act = policy.action(obs_frame) → (필터) → make_robot_action(...)
    else:       act = teleop.get_action()    # 리더 팔 위치
    robot.send_action(act)                  # omx_safe_start가 바꿔 끼운 send_action
    dataset.add_frame({관측, 동작, task})   # 영상은 이 순간 압축기로 바로 들어감
    due += 1/fps; precise_sleep(due - 지금)

    한 스텝이 1/30초를 넘으면 Record loop is running slower 경고를 찍고, 크게 밀리면 일정을 지금부터 다시 잡습니다(밀린 프레임을 몰아 찍지 않음).

  4. 에피소드 사이 (run_episodes · reset_period)

    • 녹화: 원위치 시간에도 리더를 계속 따라갑니다(기록 없음).
    • 평가: OMX_RESET_HOME=1이면 go_home_all로 두 팔 모두 처음 자세로 돌아가고, 그동안 카메라만 따로 읽어(_feed_live_view) 화면과 물체 위치 감지가 멈추지 않게 합니다.
    • 저장: save_episode가 규칙을 적용합니다. 중단된 시도는 1초 이상이면 '중단됨'으로, 빈 에피소드는 건너뜀. 저장되는 에피소드마다 관절 데이터를 따로 백업합니다(.omx_backup/…/episode_000003.npz, 강제 종료로 parquet가 깨져도 분석 가능).

  5. 끝 (run의 finally)

    Stop recording → dataset.finalize() → robot.disconnect(). 이 disconnect가 안전 정지입니다: 평가면 처음 자세로 → 그리퍼 정리 → 출력 3초에 걸쳐 감소 → 토크 끔. 비상 정지 상태라면 여기서 [홈 위치로 이동]을 기다립니다. 마지막에 os._exit(0)으로 바로 끝내는데, 파이썬 정리 단계에서 카메라 스레드 때문에 가끔 비정상 종료 코드가 나던 문제를 피하기 위해서입니다.

실시간 카메라 화면은 어떻게 보이나

녹화 중에는 omx_run.py가 카메라를 쥐고 있어서 서버가 직접 열 수 없습니다. 그래서 omx_run.py의 쓰기 스레드가 초당 약 10번 최신 프레임을 JPEG로 /dev/shm/omx_live_<uid>_front.jpg(메모리 위 파일)에 쓰고, 서버의 /stream/front가 그 파일을 MJPEG로 브라우저에 흘려보냅니다. fps·밝기(omx_camstats)도 0.5초마다 …_stats.json으로 같은 방식입니다. 녹화가 아닐 때 [카메라 보기]를 켜면 서버의 Preview가 직접 카메라를 열어 같은 파일을 씁니다.

06

흐름 ④: 제어 PC ↔ GPU 노트북

설정에 "role": "control"인 PC에서 서버가 켜지면 omx_remote.TUNNEL.start()가 SSH 연결 하나를 열고 유지합니다(Wi-Fi가 끊기거나 절전 후에도 다시 연결).

ssh -N -L 127.0.0.1:8795:127.0.0.1:8765   # 내 제어판 포트+30 → GPU 노트북의 내 계정 제어판
       -L 127.0.0.1:8796:127.0.0.1:8790   # 내 제어판 포트+31 → 내 계정 추론 서버(GPU 제어판 포트+25)
       omx-gpu                              # 설치 때 만든 SSH 별칭(Tailscale 주소 + 키)

API 넘기기 (Handler._forward)

화면은 항상 이 PC의 서버에만 요청합니다. 서버는 아래 경로를 받으면 직접 처리하지 않고 터널 너머 GPU 노트북 제어판에 그대로 보내 그 답을 돌려줍니다. 그래서 학습 탭·비교·보고서는 제어 PC에서도 같은 화면으로 쓰입니다.

PROXY_GET  = ("/api/train/", "/api/eval/compare", "/api/eval/report", "/report/", "/api/presets")
PROXY_POST = ("/api/train/", "/api/eval/compare", "/api/eval/report", "/api/presets/", "/api/home/task")

데이터 보내기 (sync_dataset · sync_loop)

  • 녹화·평가가 끝나면 rsync로 GPU 노트북의 /srv/il/lerobot_data/<GPU 계정>/<이름>에 복사합니다. GPU 쪽 파일은 지우지 않습니다(추가·변경만).
  • 같은 이름이 이미 있는데 다른 곳에서 만든 데이터면 보내지 않습니다. 데이터셋 안의 .omx_origin(PC 이름+계정)로 구별합니다.
  • 보낸 결과는 데이터셋 안 .omx_sync.json에 남기고(GPU로는 안 감), sync_loop가 1분마다 실패했거나 아직 안 보낸 것을 다시 보냅니다. 에피소드 0개, 임시 사진 폴더(images/)는 보내지 않습니다.
  • 평가 결과 표시(성공/실패 등)는 .omx_notes/eval_….json에 있고, 바꿀 때마다 2초 뒤 sync_note로 보냅니다.

모델 고르기

평가할 모델 목록은 GPU 노트북의 학습 기록(/api/train/runs, 넘기기)에서 옵니다. 고르면 fetch_model이 그 모델의 설정 파일 두 개(config.json, train_config.json)만 ~/.cache/omx/models로 가져옵니다. 정책 종류·카메라 이름·관절 수를 확인하는 데만 쓰고, 가중치는 GPU 노트북에만 있습니다.

07

흐름 ⑤: 평가 때 AI 추론이 오가는 길

제어 PC에는 GPU가 없으므로, 30Hz로 로봇을 움직이는 루프는 제어 PC에서 돌고 "다음 동작 묶음 계산"만 GPU 노트북에 부탁합니다. 매 프레임을 보내지 않고, 묶음이 떨어져 갈 때만 그 순간의 관측을 보냅니다.

  1. 평가 시작 (omx_web.start_eval → remote_eval_settings)

    모델과 설정을 확인하고(관절 6개=단일, 12개=협동, 카메라 이름 일치: check_model_fits), 추론 설정을 환경 변수로 만들어 omx_run.py에 넘깁니다.

    OMX_REMOTE_URL=http://127.0.0.1:8796     OMX_REMOTE_MODEL=/srv/il/checkpoints/tkoo/…/pretrained_model
OMX_REMOTE_OVERRIDES={"diffusion_steps": 10, "n_action_steps": 15}
OMX_ASYNC=1  OMX_ASYNC_CHUNK=15  OMX_ASYNC_THRESHOLD=0.90  OMX_ASYNC_AGG=latest_only

    비동기를 켜지 않은 기본("동기") 실행도 원격에서는 엔진을 씁니다. 다만 묶음을 거의 다 쓴 뒤, 약 0.5초(네트워크 왕복 한 번) 전에 다음 묶음을 요청하게 합니다: threshold = min(0.9, 15 / 묶음 크기). ACT(묶음 100)는 0.15, Diffusion(15)은 0.9입니다.

  2. 모델 미리 불러오기 (Policy → RemoteClient.load)

    /load를 보내 GPU에 모델을 올립니다(SmolVLA는 처음 수십 초). 서버는 모델이 원하는 영상 크기(Diffusion은 240×320으로 줄여 받음)와 관측 개수(Diffusion 2장, 나머지 1장)를 알려 줍니다.

  3. 매 스텝 (AsyncRunner.step)

    큐에 남은 동작 ≤ threshold × 묶음  그리고  추론 중이 아니면
    → 배경 스레드에서 _infer(t0, 최근 관측)      # 로봇은 큐의 동작으로 계속 움직임
큐에서 이번 스텝 동작을 꺼내 돌려줌
큐가 비었으면 → 추론이 끝날 때까지 기다림(기다린 횟수로 기록)

    새 묶음이 오면 _merge가 이미 지나간 스텝은 버리고, 겹치는 스텝은 합칩니다(weighted_average 0.3·0.7, latest_only는 새 것). RTC(SmolVLA 계열)는 아직 실행할 동작과 예상 지연을 함께 보내, 새 묶음이 이어지게 만들어진 뒤 큐를 통째로 바꿉니다.

  4. 보내는 형식 (pack_observations · encode)

    [4바이트 머리 길이][JSON 머리][JPEG, JPEG, …]
머리: {"model", "overrides", "task", "robot_type", "chunk",
       "obs": [{"state": [관절 6 또는 12개], "images": {"observation.images.front": [위치, 길이], …}}],
       "rtc": {"delay", "left"}}
답:   {"actions": 로봇용 묶음, "original": 정규화 전 묶음(RTC용), "infer_ms", "load_ms"}

    카메라 프레임은 JPEG(품질 90)로 바꿔 보내므로 카메라 4대 한 번에 약 200KB, Diffusion 2대는 약 50KB입니다.

  5. GPU 쪽 (omx_infer.serve → ModelCache → PolicyRunner.infer)

    계정마다 하나씩 떠 있는 추론 서버(127.0.0.1 전용)가 받습니다. allowed_model로 팀 체크포인트 폴더 안 모델만 허용하고, ModelCache가 최근 모델 2개를 GPU에 올려 둡니다. PolicyRunner.infer는 LeRobot의 전처리기 → policy.predict_action_chunk → 후처리기를 거쳐 묶음을 만듭니다. Diffusion은 관측 2장을 정책 내부 큐에 직접 채워 넣습니다.

  6. 로봇으로 (control_loop)

    꺼낸 동작 텐서를 make_robot_action으로 관절 이름 dict로 바꿔 robot.send_action, 그리고 데이터셋에 기록합니다. 10초마다 [omx] async: 추론 …ms … 원격: 왕복 …ms (GPU 추론 …ms)를 찍습니다.

측정 (2026-10-28, 시험 환경)왕복GPU 계산결과
협동 ACT, 카메라 4대, 묶음 100370~640ms약 22ms30Hz 유지, 큐가 빈 경우 시작 때 1~2회
단일 Diffusion DDIM 10, 카메라 2대, 묶음 15150~330ms약 92ms왕복이 0.25초 안이면 30Hz. 넘으면 끊김(묶음 0.5초 분량의 한계)

GPU 노트북에 로봇을 직접 꽂아 쓰는 경우에는 추론 서버를 거치지 않고 같은 프로세스에서 PolicyRunner를 씁니다. 비동기를 켜면 같은 엔진, 끄면 매 스텝 PolicyRunner.select(정책의 select_action, ACT 시간 앙상블 포함)입니다.

08

흐름 ⑥: 학습

  1. 학습 탭 → GPU 제어판

    [학습 시작]은 /api/train/start입니다. 제어 PC에서는 넘기기로 GPU 노트북 제어판의 train_start가 받습니다. make_job이 설정을 검사해(스텝 100~500,000, 배치 1~64, 평가 데이터는 학습 후보로 체크한 시도만) 작업 파일 train_job_….json을 만들고 omx_train.py를 독립 프로세스로 띄웁니다. 제어판이 꺼져도 학습은 계속됩니다.

  2. 학습 데이터 만들기 (omx_train.py 1단계)

    데이터셋 하나를 그대로 쓰면 그대로, 빼는 에피소드가 있거나 여러 개면 lerobot-edit-dataset으로 빼고(delete_episodes) 합쳐서(merge, 0.6.1은 결과 이름이 --new_repo_id) <계정>/train_<키워드>_<날짜>를 만듭니다. 어느 원본의 몇 번 에피소드인지 meta/omx_sources.json에 남깁니다. 같은 조합을 전에 만들었으면 다시 씁니다.

  3. lerobot-train (2단계)

    lerobot-train --dataset.repo_id=tkoo/train_… --policy.type=act --policy.device=cuda --policy.push_to_hub=false
  --output_dir=/srv/il/checkpoints/tkoo/<이름> --steps=40000 --batch_size=8 --num_workers=8
  --log_freq=100 --save_freq=10000 --env_eval_freq=0 --wandb.enable=false
  # Diffusion: --policy.resize_shape=[240, 320] --policy.crop_ratio=0.95
  # SmolVLA: --policy.path=lerobot/smolvla_base --rename_map={front→camera1, wrist→camera2}

    run_logged가 출력의 진행 막대(51/100 [00:15<00:09, 5.14step/s])와 loss: 줄을 읽어 train_state.json에 쓰고, 화면은 2초마다 이것을 읽어 그래프를 그립니다.

  4. 정리 (3단계)

    마지막 모델을 <run>/pretrained_model로 복사, summary.json(학습자, 시간, 최종 loss, 데이터 지문)과 train.log를 남기고, 팀 그룹 권한을 주고, omx_index.py로 INDEX.md를 갱신합니다.

학습 계획(omx_train_queue.py)은 여러 건을 한 줄로 세워 두고 GPU가 비면 차례로 omx_train.py를 돌립니다. GPU 하나에서 학습은 한 번에 하나만 돕니다(다른 계정의 학습도 확인).
